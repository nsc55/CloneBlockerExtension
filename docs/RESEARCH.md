# Research: can a content script use Facebook's / Threads' internal JavaScript?

**Short answer: yes, and it is the difference between a fragile extension and a durable one.**

Everything below was verified empirically against live `facebook.com` and `threads.com`
on 2026-08-20 (Chrome 151), not taken from documentation. Where something could not be
verified first-hand it is marked **UNVERIFIED**.

No Facebook/Threads SDK and no Graph API is used anywhere in this project.

---

## 1. The module registry is reachable, and it is the key to everything

Meta ships its web apps as an AMD-style bundle. Modules register through a global
`__d(name, deps, factory)` and are read back with `require(name)`. Both are plain
properties on the page's `window`:

```js
typeof window.__d          // "function"
typeof window.require      // "function"
typeof window.requireLazy  // "function"
```

A MAIN-world content script running at `document_start` executes **before** Meta's
bootstrap, which means it can intercept every module registration:

```js
Object.defineProperty(window, '__d', {
  configurable: true,
  get() { return realD ? proxy : undefined; },
  set(v) { realD = v; }          // Meta assigns; we wrap what they assigned
});
```

Measured in the shipped extension's own test run:

| Site | modules registered | `*.graphql` modules |
|---|---|---|
| facebook.com (logged out) | 2,728 | 33 |
| threads.com profile page | 4,869 | 578 |

### Why this matters: `doc_id`s are discoverable at runtime

Meta's GraphQL is persisted-query only — requests carry a numeric `doc_id`, not a query
string, and those ids rotate roughly monthly. Hardcoding one guarantees breakage.

But each Relay operation is itself a module, and requiring it hands back the live id:

```js
require('useCometLocaleSelectorLanguageChangeMutation.graphql').params
// -> { id: "29960775910235124",
//      name: "useCometLocaleSelectorLanguageChangeMutation",
//      operationKind: "mutation" }
```

Verified on both sites. So **this project never hardcodes a `doc_id`** — it reads the
current one out of the page at call time.

## 2. Tokens come from internal modules, with HTML fallbacks

```js
require('LSD').token                    // -> "<a 27-char token, redacted>"  (verified)
require('DTSGInitialData').token        // fb_dtsg
require('CurrentUserInitialData')       // { USER_ID, ACCOUNT_ID, APP_ID, ... }  (verified)
```

Because Meta occasionally renames these modules, every lookup in `src/main/inject.js`
falls back to a regex over the served HTML.

**A hand-built request really is accepted.** Posting to `/api/graphql/` with only
`lsd` + `doc_id` + `variables` returned:

```
missing_required_variable_value
```

That is a *query-execution* error, not an auth error — the request passed CSRF/LSD
validation and reached the GraphQL executor.

## 3. Endpoints (verified from real captured traffic)

| Platform | Endpoint |
|---|---|
| Facebook | `POST https://www.facebook.com/api/graphql/` |
| Threads | `POST https://www.threads.com/graphql/query` |

Threads additionally sends `x-ig-app-id: 238260118697367`, `x-asbd-id`,
`x-fb-lsd`, `x-csrftoken`, `x-fb-friendly-name`, and `x-root-field-name` (root fields are
`xdt_`-prefixed, e.g. `xdt_threads_logged_out_feed`).

### The trap that makes hand-built requests fragile

A real captured Threads request body carried **~30** variables of the form:

```
__relay_internal__pv__BarcelonaIsLoggedInrelayprovider=false
__relay_internal__pv__BarcelonaHasCommunitiesrelayprovider=true
… 28 more …
```

These are Relay *provider variables*, generated by the client at build time. You cannot
reliably reconstruct them, and omitting one produces exactly the
`missing_required_variable_value` error above. This is the single strongest argument
against hand-rolling requests.

## 4. The best mechanism: drive Meta's own Relay runtime

Rather than building a request, ask Relay to do it:

```js
require('RelayModern').commitMutation        // typeof "function"   (verified)
require('CometRelayEnvironment')             // live env, Facebook  (verified)
require('BarcelonaRelayEnvironment')         // live env, Threads   (verified)
```

Both environments expose `getStore()` and carry the `@@RelayModernEnvironment` marker.
The test run found `BarcelonaRelayEnvironment` holding **593 live records** on a Threads
profile page.

Committing through Relay means Relay supplies the `doc_id`, every provider variable,
`fb_dtsg`, `lsd`, and all the `__dyn`/`__csr` bookkeeping — *and* updates the local store,
so the UI reflects the change immediately. This is Strategy A in `src/main/inject.js`.

## 5. The Relay store solves profile-ID resolution

The hardest practical problem is that **Facebook rarely puts a numeric profile ID in the
DOM**. Vanity URLs render as `facebook.com/someone` with no id anywhere, and Comet's
old `data-hovercard` attribute is gone.

The Relay store has it. A record sweep on a Threads profile returned:

```json
{
  "recordKey": "XDTUserDict:63082166531",
  "id": "63082166531",
  "pk": "63082166531",
  "username": "threads",
  "fields": ["friendship_status", "follower_count", "is_verified", …]
}
```

That gives a live **id ↔ username** map for everything on screen, plus
`friendship_status.blocking` — the profile's *current* block state — with no extra
network requests. The extension sweeps this periodically and caches the mapping in
`chrome.storage`, so a list expressed in IDs still matches a page that only shows
usernames (and vice versa).

Facebook also encodes GraphQL node ids as `base64("User:12345")`, which the extension
decodes as a secondary source.

## 6. What the ISOLATED world cannot do (why MAIN world is required)

Three hard blockers, all confirmed:

1. **`window.require` / `__d`** live on the page's window. The isolated world has a
   different window object entirely.
2. **React fiber expandos** (`__reactFiber$…`, `__reactProps$…`) are invisible across
   worlds — each world gets its own JS wrapper for the same DOM node.
3. **The Relay environment and store** are page-realm objects.

MAIN-world content scripts get **no `chrome.*` APIs at all**, so the two halves must
talk over `window.postMessage`. That is what `src/content/bridge.js` does.

### CSP

Both sites serve a strict nonce-based `script-src`:

```
script-src *.facebook.com *.fbcdn.net *.facebook.net 'nonce-dVl9XHEp' blob: 'self' …
connect-src *.threads.com *.threads.net …
```

So injecting a `<script>` tag from a content script is the wrong approach — the manifest's
`"world": "MAIN"` (Chrome 111+) is the correct one, since the browser injects it directly.

The restrictive `connect-src` is also why **the blocklist is fetched in the service
worker, never from the page**: a MAIN-world fetch to your server would be blocked by the
page's CSP, and a content-script fetch is bound by facebook.com's origin. Service-worker
fetches only need `host_permissions` and are exempt from CORS.

## 7. Known block operations

Facebook's profile Block button uses **`ProfileCometActionBlockUserMutation`**:

```json
{
  "collectionID": null,
  "hasCollectionAndSectionID": false,
  "input": {
    "blocksource": "PROFILE",
    "should_apply_to_later_created_profiles": false,
    "user_id": 12345,
    "actor_id": "<your id>",
    "client_mutation_id": "1"
  },
  "scale": 3,
  "sectionID": null,
  "isPrivacyCheckupContext": false
}
```

The settings surface uses `BlockingSettingsBlockMutation` with an explicit
`block_action: "BLOCK" | "UNBLOCK"`.

These names are used only as *hints* — to rank discovered modules and to shape variables.
The `doc_id` is always read live.

### Threads: now VERIFIED against a signed-in account

Captured by watching a real block leave the browser, then reproduced by the
extension itself:

```
POST https://www.threads.com/api/graphql
fb_api_req_friendly_name = useTHUserBlockMutation
doc_id                   = 26803837702651619      (rotates; read at runtime)
variables = {"user_id":"<pk>","container_module":"ig_text_feed_profile",
             "media_id":null,"ranking_info_token":null,
             "barcelona_source_quote_post_id":null,"barcelona_source_reply_id":null,
             "is_messaging_nua":null,"consistent_thread_fbid":null}
```

Four assumptions this overturned, each of which had looked reasonable:

1. **The operation is `useTHUserBlockMutation`, not `Barcelona*`.** Threads' codename
   prefixes most of its modules, but not this one.
2. **Mutations go to `/api/graphql`, not `/graphql/query`.** Threads uses both: reads
   (feed pagination) go to `/graphql/query`, writes to `/api/graphql`. A mutation sent
   to the read endpoint cannot work.
3. **The variables are flat** — no `input` wrapper and no `actor_id` — structurally
   unlike the Facebook mutation.
4. **The Instagram REST paths do not exist here.** Both
   `/api/v1/friendships/block/{pk}/` and `/web/friendships/{pk}/block/` return 404.

### Raw requests can cost you the session

Worse than not working: posting a hand-made, CSRF-token-bearing request to those
non-existent REST paths coincided with Meta invalidating the signed-in session —
twice, reproducibly, with nothing else in flight. Driving the site's own Relay code
never did.

That is why raw fallbacks now sit behind `allowRawNetworkFallback`, off by default,
and why the REST paths were removed from the ladder outright. A fallback that cannot
succeed and can log the user out is a liability, not a safety net.

### Facebook: also VERIFIED

```
POST https://www.facebook.com/api/graphql/
fb_api_req_friendly_name = ProfileCometActionBlockUserMutation
doc_id                   = 27612956954991359     (rotates; read at runtime)
variables = {"collectionID":null,"hasCollectionAndSectionID":false,
             "input":{"blocksource":"PROFILE","should_apply_to_later_created_profiles":false,
                      "user_id":<target>,"actor_id":"<viewer>","client_mutation_id":"<n>"},
             "scale":3,"sectionID":null,"isPrivacyCheckupContext":false}
```

Unlike Threads, the operation name and variable shape sourced from third-party code
were **correct** here. Only the `doc_id` differed, as expected -- the 2024-era value in
circulation was `6305880099497989`, which is exactly why it is read live rather than
pinned.

Verified end to end: the extension blocked via `commitMutation`, the profile switched to
"This content isn't available right now", and the target appeared in Facebook's own
Settings -> Blocking -> "See your blocked list". Unblocking through that same UI restored
the profile. The session survived throughout.

Same lazy-loading constraint as Threads, and slightly stricter: on Facebook the module
appears only once the block **confirmation dialog** is raised. Opening the profile's
overflow menu is not enough.

One irreversible side effect worth knowing: blocking consumes a pending friend request,
and unblocking does not restore it. Blocking an existing friend removes the friendship
the same way. Facebook's own dialog says as much -- "blocking it will unfriend, unlike
and unfollow it".

### The Relay path works, and is safe

Verified end to end: the extension performed a real block through
`RelayModern.commitMutation` using Threads' own operation node, the block took effect
(`friendship_status.blocking: true`, the profile switched to "Unblock"), and **the
session survived**.

One constraint, confirmed empirically: `require('useTHUserBlockMutation.graphql')`
resolves only after the block UI has been opened once in that page load. Meta ships
the module lazily, and neither `Bootloader.loadModules` nor `requireLazy` can pull it
by name — both time out, because the loader needs a resource map that only ships when
a component needing it renders.

**Re-measured 22 August 2026, and then routed around.** The constraint is real and is
tighter than the note above: `requireDeferred` and `JSResource` are not globals on
threads.com at all; `Bootloader.loadModules`, `requireLazy` and
`SecuredActionBlockDialog.entrypoint.root.load()` each return without defining the
module; a hidden iframe is refused (`X-Frame-Options: DENY`); and the module now arrives
with the confirmation dialog behind the menu's Block item rather than with the menu.

But the operation node is only needed by `commitMutation`. **`environment.getNetwork()
.execute(params, variables, {force: true})` takes plain RequestParameters** — `{id, name,
operationKind}` — so a persisted-query doc_id is enough, and the site's own network layer
composes everything else. Proven twice on the live site: a query executed from
hand-built parameters returned data, and `useTHUserBlockMutation` itself, aimed at
`user_id: "0"`, was accepted and executed, failing on the server's own validation
(`blocked is None`) with the session intact. What it gives up against `commitMutation` is
the provider variables Relay injects from the node — the Threads block mutation declares
none — and the store write that redraws the UI.

**Dead ends:** `mbasic.facebook.com` (retired December 2024, so
`/privacy/block/confirm/?bid=` is gone) and the pre-Comet `ajax/privacy/block_user.php`.

## 8. Because names rotate, the extension learns instead of assuming

Meta loads the block mutation module lazily — it is not present until the user opens a
profile's menu. So a name-based lookup can legitimately find nothing.

The fallback is observation: the MAIN world hooks **both `fetch` and `XMLHttpRequest`**
(Meta uses both on different surfaces), watches for a block-shaped request, and stores the
complete field set — provider variables and all. Blocking one person by hand teaches the
extension the exact request shape, which it can then replay against other ids.

Strategy ladder, best first:

1. **Relay `commitMutation`** — Relay fills in everything.
2. **Replay a captured template** — provider variables preserved verbatim.
3. **Threads REST friendships** — no `doc_id` involved at all.
4. **Hand-built GraphQL** — runtime-discovered `doc_id`, or one your server pushes via
   `docIdOverrides` so you can hot-patch a rotation without shipping a new build.

---

## 9. Rate limiting

No public source gives hard numbers for block-rate thresholds, so the defaults here are
deliberately conservative (15/hour, 60/day, 20–45s randomised gaps) rather than
evidence-based. **UNVERIFIED.** The extension detects `429` and checkpoint/challenge
responses, backs off, and disables platform blocking outright on a checkpoint.

Hiding carries zero account risk but does nothing about the clone itself, so it is an
opt-in extra; real blocking is the default, rationed by the passive/active modes and
with a dry-run mode for verifying the strategy before anything is sent.
